# Architecture notes

## Accounts and encryption

The app is private: an account can only be created with an invitation. The first account is created with the admin code generated by `npm run setup`. Invitations are single-use and expire after 7 days; the admin page (and `npm run admin`) lists accounts, creates password reset codes and removes an account with all its data.

**Password.** The phone runs PBKDF2-SHA256 (600,000 iterations, the OWASP recommendation) then HKDF to derive two keys. The login key goes to the server, which keeps only a salted HMAC of it. The data key never leaves the phone and encrypts the backup (compressed, then AES-GCM). Neither the server nor the admin can read passwords or the logged workouts and meals. What the server does see in clear is what reminders need: the day's summary, reminder times, and the steps and energy sent by Apple Health.

Accepted trade-off: after a forgotten password, the old backup cannot be decrypted. It is wiped and rebuilt from the data still on the phone. Changing the password from the app re-encrypts the backup without loss.

**Sign-out** makes a last backup, stops notifications for this device and clears the phone, so a borrowed phone keeps nothing. If two devices changed the data, the app asks which version to keep.

**KV layout**

| Key | Content |
| --- | --- |
| `acct:<id>` | email, first name, role, salt and HMAC of the login key |
| `email:<sha256>` | email → id (emails never appear in clear in keys) |
| `idx:users` | account list, for reminders and the admin page |
| `sess:<sha256>` | sessions (180 days); only the token hash is stored |
| `dkey:<sha256>` | iOS Shortcuts key, limited to health and gym endpoints |
| `inv:…`, `rst:…` | invitations (7 days) and reset codes (48 h) |
| `u:<id>:…` | per-user data: encrypted backup, push subscription, reminder times, day summary, health, gym, AI quota |

## Coach memory (retrieval)

Before each question, the app looks for the pieces of history that answer it and sends only those to the model. This makes the coach more precise and cuts the tokens sent.

- **Local search** (`src/lib/knowledge.ts`): history is split into documents (a day, a week, one exercise's history, weight, profile, past conversations) and indexed on the phone with BM25, recency and synonyms ("pecs" → bench, dips, flyes; "yesterday", "Monday", "12/10"). Free, offline, nothing leaves the phone.
- **API mode**: snippets are sent with the question, and the answer shows what it relied on.
- **Claude app mode**: no API cost; the app opens the Claude app with the question, the day's context and the snippets, as long as the link stays under the length limit.
- **Long-term memory without an API key**: "Export my file" produces a Markdown file to add to a Claude Project's knowledge.
- **Later**: with months of free text, embeddings can replace the local search by implementing the `Retriever` interface (for example Workers AI `bge-m3` and Vectorize). For workout and meal data, local search is enough.

## Reminders

`worker/reminders.ts` decides what to send; `worker/webpush.ts` signs (VAPID, ES256) and encrypts (`aes128gcm`, RFC 8291) the payload. The cron runs every 15 minutes, skips users whose day is already complete, avoids duplicates and deletes subscriptions the push service reports as gone. The workout reminder is skipped when a gym check-in says you are already there.

## Apple Health and gym check-ins

A PWA cannot read Apple Health; only native apps can. The bridge is the iOS Shortcuts app, free and without a developer account.

- A **Shortcuts key** (Settings) goes in the shortcuts' `Authorization` header and only allows health and gym endpoints.
- **Shred Health** reads the day's totals (steps, active and resting energy, grouped by day so iPhone and Apple Watch are not counted twice) and POSTs them to `/api/health/ingest`. The server keeps the highest total of the day, so an empty send (locked iPhone) erases nothing, and writes at most once per quarter hour for small changes to stay within the free KV write quota.
- **Arrival / Departure** automations on the gym's address call `/api/gym/checkin` and `/api/gym/checkout`. On arrival, a notification opens today's workout.

```json
{
  "steps": 8432, "active_kcal": 412.5, "resting_kcal": 1715,
  "sleep_h": "7,2", "resting_hr": 56, "hrv": 63, "exercise_min": 34, "distance_km": "5,8",
  "date": "2026-10-13"
}
```

Every field is optional. French-formatted numbers ("8 432", "412,5 kcal", "6 h 45") are accepted; `sleep_min` works instead of `sleep_h`; `date` is optional (today by default, up to 7 days back). Cumulative values (steps, energy, exercise minutes, distance) keep the highest total of the day; sleep, resting heart rate and HRV keep the latest value. A short night, an HRV 20 % under the 14-day average or a resting heart rate 5 bpm above it makes the workout screen suggest the "tired" mode.

## Backup merge

When the phone and the account hold different data (two devices, or a phone used offline), `src/lib/merge.ts` merges them instead of asking which one to overwrite: days are united and, for a day present on both sides, sets keep the longest log per exercise, meals are united by id, habits and "session done" are OR-ed. Weigh-ins, waist, health and photo metadata are united too. Settings, program and meal plan come from the side edited most recently. A copy of the phone's state is kept in `localStorage` (`shred:before-merge`) before each merge.

## Rest timer notifications

A web app cannot schedule a local notification on iOS. When a set is checked, the app asks the Worker to notify it at the end of the rest; a Durable Object (`worker/timers.ts`, one per user) sets an alarm and sends the Web Push at that second, so it arrives on a locked phone. If the app is on screen three seconds before the end, it cancels the alarm and the on-screen timer is enough.

## Club

`worker/club.ts`. One Durable Object (`CLUB`, SQLite-backed, a single instance named `club`) serialises every write, so spark and comment counters never race. Keys: `p:<timestamp>:<id>` (posts, listed newest first with `reverse`), `pid:<id>` (index), `c:<post>:<timestamp>:<id>` (comments), `f:<user>` / `fb:<user>` (following / followers), `n:<user>:<timestamp>:<id>` (notifications), `nr:<user>` (read marker), `count:<user>`, `sp:<user>` (sparks received, turned into XP by the app: 5 each; no spark on your own post), `ch:<id>` and `chu:<user>:<timestamp>:<id>` (challenges: one session to validate within 24 h, 48 h or 7 days, at most two open from one member to another; the app marks them done when the challenged member validates a session in time, worth 20 XP, and the challenger is notified). The Worker authenticates, checks mentions against the member list, stores photos in KV (`club:photo:<id>`, data URLs decoded and size-checked, 4 per post) and sends Web Push for mentions, comments and new followers.

Visibility per post: the whole club, followers only, or only me; people tagged in a post can always see it. Posts carry a summary prepared by the app (title, up to 6 stats, an intensity profile as `[zone, seconds]` pairs, records), sanitised and bounded on the server. The encrypted backup is never read. Deleting an account removes its posts, comments, photos, avatar and follows.

## Strava and native Health

- `worker/strava.ts`: OAuth (`/api/strava/connect`, `/api/strava/callback` with a one-time state in KV), token refresh, `/api/strava/sync` returning short activity summaries. Tokens never leave the server. See [STRAVA.md](STRAVA.md).
- `src/lib/activities.ts`: activities from Strava or the Apple Watch land in `day.activities`, de-duplicated (same id, or same sport within 10 minutes from another source). An activity of the session's sport ticks those blocks off (and the session when it is complete); `linked` records which blocks it stands for, so the stats count the real distance and time instead of the plan's estimate, once.
- `src/lib/nativeHealth.ts`: in the iPhone app (`isNative()`), HealthKit daily aggregates, sleep samples and workouts are read on each launch and when the app comes back to the foreground; today's totals are also sent to `/api/health/ingest` for the reminders. See [IOS.md](IOS.md).

## Training logic

- **Daily goal**: by default today's session (or active rest) and at least 3 logged meals. Configurable.
- **Freezes**: 1 to start, +1 every 7 streak days, 2 max. A missed day uses a freeze instead of breaking the streak.
- **Flames**: the first one after 3, 7, 14 or 30 days (user's choice), then increasingly spaced milestones. Each one changes the flame's colour and is kept even if the streak breaks.
- **Load progression**: when every set reaches the top of the rep range, the app suggests the next load (+2.5 kg, +5 kg on squats and deadlifts). A load typed on one set is copied to the following sets not yet done.
- **Strength profile** (`src/lib/strength.ts`): best set of the last 8 weeks on reference lifts, estimated 1RM (Epley, reps capped at 15), relative to body weight, graded A to E against beginner-to-advanced standards.
- **Needs** (`shared/athlete.ts`): Mifflin-St Jeor BMR, daily activity and training sessions; cut, recomp, maintenance or bulk; protein relative to lean mass when body fat is known.
- **Race plans** (`shared/plans.ts`): 5K, 10K, half and full marathon dated to race day (6, 8, 12 or 16 weeks, shortened if the date is close), base, build, specific and taper phases, a deload week every 4 weeks, paces from a recent time (Riegel). Hyrox: 12 weeks.
- **Endurance plans** (`shared/endurance.ts`): swimming, cycling, triathlon and running without a race date. A weekly layout per sport and number of days (2 to 6, 3 to 7 for triathlon) places quality, long, easy and strength sessions; each week is built from its phase (base, build, specific, taper), a recovery week every 4 weeks, the athlete's level and, for 8-week blocks, the block number (+6 % volume per block). Paces come from a recent run time (Riegel), the swim CSS (from a 400 m time) and the bike FTP when known (otherwise % FTP and perceived effort). Weekday sessions are capped by the available minutes before recovery and taper scaling, so those weeks always get lighter.
- **Effort model** (`shared/effort.ts`): every endurance block has a sport and a zone (1 to 5) and an estimated duration (from the plan's paces, or default paces per sport and zone). It draws the session profile, computes the session length and estimates distances for the stats.
- **Training stats** (`src/lib/training.ts`): minutes per sport from the checked sets (lifting at 40 s per set plus rest, endurance from the logged time or the block's estimate), distances per sport, calendar weeks for the load chart and rolling 7-day windows for the distance tiles, best set per session as an estimated 1RM curve with records.
- **Gyms**: equipment is ticked per gym; each impossible exercise is replaced by the best available equivalent.
- **Meal plan** (`shared/meals.ts`): about thirty recipes built from common foods, portions scaled to macros, two batch-cooking days, a shopping list by aisle, dietary filters.
- **Weekly report** (`src/lib/report.ts`): sessions done vs planned, completed days, average calories and protein, weight trend vs target, records and stalling lifts, with one-tap adjustments. Computed on the phone (the server only holds encrypted data) and optionally emailed through Resend.

## Free plan watch (`worker/usage.ts`)

Every API request runs with a metered `env`: KV gets, puts, deletes and lists, and Durable Object calls, are counted in the isolate and sent to the `USAGE` Durable Object (SQLite, single instance) at the end of the request, at most every 30 s unless something was written. Totals are kept per UTC day (Cloudflare resets at 00:00 UTC) with KV writes broken down by use (`santé`, `sauvegarde`, `état du jour`…), 35 days of history.

The KV write budget (1,000 per day on the free plan) is the tightest one, so the small counters that used to write to KV live in `USAGE` instead (100,000 SQLite rows per day): AI requests per user per day, login and signup attempts, reminders already sent. The mode follows the day's KV writes (or requests): normal below 60 %, economy from 60 % (health saved at most hourly, one backup per person per 30 min), critical from 90 % (health every 3 h, backup every 2 h). Data stays on the phones in the meantime. Admins get one push per day and per level. `GET /api/admin/usage` returns the last 14 days with limits and an end-of-day projection; the app shows it in Settings, Cloudflare (admins only).

## Places and music (`worker/places.ts`)

Signed-in members can search gyms anywhere in the world: `GET /api/places/gyms?lat=&lon=[&q=]` queries OpenStreetMap through Overpass (fitness centres, gyms, and sports centres tagged for fitness or combat sports) within 4 km, or 25 km when a name is given. The position is rounded to about 100 m before it leaves the Worker. `GET /api/places/geocode?q=` turns a city into a position (Nominatim) for people who refuse location access. The chosen gym is kept in `settings.gym.place`; when location access is already granted and the phone is within 150 m of it, the Today screen offers to start the session (once a day, never asks for permission on its own).

`GET /api/music/search?q=&country=` searches the iTunes Search API (songs, 30 s previews, no key). A post can carry one track; the Worker only accepts Apple hosts for the artwork, preview and link. All three lookups are cached for a day in the Cloudflare cache, which costs no KV writes.
